Naskah Seri Git dan Kerja Tim (G01-G06)
 · 
Cara membaca naskah
Kolom Narasi (Cahaya) adalah teks yang dibacakan suara, jadi hanya kolom itu yang memakai kredit. Kolom Visual adalah petunjuk rekaman dan diagram. Ibu boleh menyunting langsung di dokumen ini; saya akan membaca versi terakhir sebelum produksi.
Proyek contoh: SiAntre, aplikasi antrean bengkel dari video "Sistem Antrean dari Nol". Untuk seri ini dipakai versi kecilnya: server.js (Express), public/index.html, antrean.js (fungsi ambilNomor dan formatNomor), dan berkas .env.
Tokoh: Raka mengerjakan backend, Nadia mengerjakan tampilan. Mereka tidak muncul sebagai gambar, hanya sebagai nama di git config dan di riwayat commit. Di G05 dan G06 layar dibagi dua: terminal Raka di kiri, terminal Nadia di kanan.
Diagram graf commit: titik bulat = commit (dengan 7 huruf awal hash), panah ke commit sebelumnya, label berwarna = branch, label hitam "HEAD" = posisi kita sekarang. Graf bergerak tepat saat perintah dijalankan di terminal.
Tebak dulu: layar berhenti di perintah yang belum dijalankan, muncul tulisan "Tebak dulu" dengan hitung mundur 5 detik, lalu perintah dijalankan.
Perintah berbahaya (reset --hard, push --force) selalu diberi label merah "Hati-hati: menghapus".
G01 Git dari Nol: Commit Pertamamu
Kait: "Setelah menonton, kamu bisa menyimpan setiap langkah kerjamu dengan Git dan melihat persis apa yang berubah."
No
 | Bagian
 | Narasi (Cahaya)
 | Visual
 | 
1
 | Kait
 | Kemarin aplikasimu masih jalan. Hari ini, setelah kamu mengubah beberapa baris, aplikasinya rusak, dan kamu lupa bagian mana yang kamu ubah. Setelah menonton video ini, kamu bisa menyimpan setiap langkah kerjamu dengan Git, dan melihat persis apa yang berubah.
 | Folder berisi app_final.js, app_final2.js, app_final_BENERAN.js; terminal menampilkan error merah. Kartu judul.
 | 
2
 | Masalah
 | Banyak dari kita menyimpan versi dengan menyalin berkas: final, final dua, final beneran. Cara ini cepat berantakan, apalagi kalau kamu bekerja berdua, atau kalau asisten AI baru saja mengubah sepuluh berkas sekaligus.
 | Berkas salinan bertambah banyak; tanda tanya di atasnya.
 | 
3
 | Konsep: commit
 | Bayangkan Git sebagai kamera untuk proyekmu. Setiap kali kamu menekan tombolnya, Git menyimpan foto seluruh proyek pada saat itu. Foto itu disebut commit. Setiap commit menyimpan pesan singkat, nama pembuatnya, waktu, dan kode unik yang disebut hash.
 | Diagram: kamera memotret folder, muncul titik commit dengan hash 3f2a9c1, pesan, nama, waktu.
 | 
4
 | Konsep: tiga tempat
 | Sebelum memotret, kamu memilih dulu apa yang masuk ke foto. Karena itu, Git punya tiga tempat. Folder kerja adalah berkas yang sedang kamu edit. Staging adalah meja tempat kamu mengumpulkan perubahan yang mau difoto. Repository adalah album tempat semua foto disimpan. Perintah git add memindahkan perubahan ke staging, dan git commit memotret isi staging ke repository.
 | Tiga kotak berjajar: Folder kerja, Staging, Repository. Panah git add dan git commit.
 | 
5
 | Praktik: config
 | Sekarang kita coba langsung pada proyek SiAntre versi kecil. Pertama, kita kenalkan diri kepada Git. Nama dan email ini tercatat di setiap commit, jadi teman satu tim tahu siapa yang membuat perubahan.
 | VS Code + terminal. Ketik git config --global user.name "Raka" dan user.email.
 | 
6
 | Praktik: init
 | Lalu kita jalankan git init. Perintah ini membuat folder tersembunyi bernama titik git, tempat Git menyimpan seluruh albumnya.
 | git init; panel Explorer menampilkan .git (dimunculkan sebentar).
 | 
7
 | Praktik: status
 | Perintah yang paling sering kamu pakai adalah git status. Git melaporkan empat berkas berwarna merah dengan tulisan untracked. Artinya, berkas itu ada di folder kerja, tetapi belum pernah disimpan Git.
 | git status, zoom ke daftar berkas merah. Diagram: 4 berkas di kotak Folder kerja.
 | 
8
 | Tebak dulu
 | Kita masukkan semuanya ke staging dengan git add titik. Tebak dulu: berkas apa saja yang ikut masuk?
 | Perintah git add . belum dijalankan; "Tebak dulu" + hitung mundur 5 detik.
 | 
9
 | Kesalahan
 | Semuanya ikut masuk, termasuk berkas titik env. Padahal berkas ini berisi password database. Kalau berkas ini ter-commit lalu diunggah, password itu bisa dibaca siapa saja.
 | git add . lalu git status: .env hijau. Buka .env, sorot DB_PASSWORD=. Label merah "Bahaya".
 | 
10
 | Perbaikan
 | Untungnya, kita belum memotret. Kita keluarkan titik env dari staging dengan git rm dash dash cached. Berkasnya hanya keluar dari staging, sedangkan berkas aslinya tetap ada.
 | git rm --cached .env; diagram: .env kembali ke Folder kerja.
 | 
11
 | gitignore
 | Supaya tidak terulang, kita buat berkas titik gitignore, lalu kita tulis titik env dan node modules di dalamnya. Sekarang Git mengabaikan berkas-berkas itu, sehingga titik env tidak muncul lagi di git status.
 | Buat .gitignore berisi .env dan node_modules/; git status tanpa .env.
 | 
12
 | Commit pertama
 | Sekarang kita potret dengan git commit dash m, diikuti pesan yang menjelaskan apa yang berubah. Git membalas dengan hash pendek commit pertama kita, dan git log menampilkan commit itu lengkap dengan nama Raka.
 | git add .gitignore, git commit -m "Buat kerangka SiAntre", git log. Diagram: titik commit pertama.
 | 
13
 | Ubah dan diff
 | Sekarang kita ubah format nomor antrean dari A1 menjadi A001, supaya mudah dibaca di layar TV. Sebelum memotret, kita periksa dulu dengan git diff. Baris merah bertanda minus adalah baris lama, dan baris hijau bertanda plus adalah baris baru.
 | Edit formatNomor di antrean.js (padStart(3, '0')), git diff, zoom ke baris -/+.
 | 
14
 | Commit kedua
 | Kita jalankan git add dan git commit lagi. Di diagram, sekarang ada dua titik, dan commit kedua menunjuk ke commit pertama. Begitulah Git mencatat urutan sejarah proyekmu.
 | Commit kedua; git log --oneline; diagram: panah dari titik 2 ke titik 1.
 | 
15
 | Kebiasaan dengan AI
 | Kebiasaan ini penting saat kamu bekerja dengan asisten AI. Lakukan commit sebelum meminta AI mengubah kode. Setelah AI selesai, periksa hasilnya dengan git diff. Kalau bagus, commit. Kalau buruk, kamu bisa kembali ke foto terakhir.
 | Diagram alur: commit, minta AI, git diff, commit atau kembali.
 | 
16
 | Rangkuman
 | Mari kita rangkum. Commit adalah foto proyek. Git add memilih isi foto, git commit memotretnya, git status dan git diff menunjukkan perubahan, dan git log menampilkan sejarahnya. Jangan lupa membuat titik gitignore sebelum commit pertama.
 | Kartu rangkuman 5 perintah.
 | 
17
 | Tantangan
 | Tantangan untukmu: buat proyek kecil, lakukan tiga commit dengan pesan yang jelas, lalu tampilkan sejarahnya dengan git log dash dash oneline. Di episode berikutnya, kita belajar mundur ke masa lalu tanpa panik.
 | Kartu tantangan + judul G02.

G02 Mundur ke Masa Lalu tanpa Panik
Kait: "Setelah menonton, kamu bisa membatalkan perubahan di Git dengan aman, bahkan menyelamatkan kerjaan yang kamu kira sudah hilang."
No
 | Bagian
 | Narasi (Cahaya)
 | Visual
 | 
1
 | Kait
 | Kamu baru saja menghapus kode yang ternyata masih dibutuhkan, atau commit terakhirmu membuat aplikasi rusak. Setelah menonton video ini, kamu bisa membatalkan perubahan di Git dengan aman, bahkan menyelamatkan kerjaan yang kamu kira sudah hilang.
 | Terminal: git log tiba-tiba hanya berisi 1 commit; wajah panik digantikan tulisan "Belum tentu hilang". Kartu judul.
 | 
2
 | Prasyarat
 | Video ini melanjutkan episode pertama, jadi pastikan kamu sudah paham commit, staging, dan git diff. Sekarang SiAntre sudah punya beberapa commit.
 | git log --oneline berisi 4 commit; diagram graf 4 titik.
 | 
3
 | Peta alat
 | Ada empat alat untuk mundur, dan masing-masing cocok untuk keadaan yang berbeda. Restore membatalkan perubahan yang belum di-commit. Amend memperbaiki commit terakhir. Revert membatalkan commit lama dengan membuat commit baru. Reset memindahkan penunjuk branch ke commit sebelumnya.
 | Diagram empat kartu alat, masing-masing menunjuk ke tempatnya: Folder kerja, commit terakhir, commit lama, penunjuk branch.
 | 
4
 | restore
 | Kasus pertama: kita tidak sengaja menghapus fungsi ambilNomor, dan perubahan itu belum di-commit. Dengan git restore, berkasnya kembali seperti di commit terakhir. Hati-hati, perubahan yang dibuang dengan restore tidak bisa dikembalikan, karena belum pernah difoto.
 | Hapus fungsi di editor, git status, git restore antrean.js; fungsi muncul lagi di editor.
 | 
5
 | amend
 | Kasus kedua: kita baru saja commit, lalu sadar ada satu berkas yang lupa dimasukkan. Kita tambahkan berkas itu, lalu jalankan git commit dash dash amend. Commit terakhir diganti dengan versi yang lengkap, dan hash-nya ikut berubah. Pakai amend hanya untuk commit yang belum dibagikan ke orang lain.
 | git add public/style.css, git commit --amend; diagram: titik terakhir diganti titik baru dengan hash lain.
 | 
6
 | Tebak dulu
 | Kasus ketiga: dua commit yang lalu, kita mengubah jam buka bengkel menjadi jam tujuh, padahal seharusnya jam delapan. Sesudahnya sudah ada commit lain yang bagus. Tebak dulu: kalau kita revert commit yang salah itu, apakah commit sesudahnya ikut hilang?
 | git log --oneline, sorot commit "Ubah jam buka". "Tebak dulu" + hitung mundur.
 | 
7
 | revert
 | Tidak ada yang hilang. Git revert membuat commit baru yang isinya kebalikan dari commit yang salah. Sejarahnya tetap utuh dan jujur, sehingga cara ini aman dipakai di branch yang sudah dibagikan ke tim.
 | git revert <hash>; diagram: titik baru "Revert ..." di ujung; git diff HEAD~1 menunjukkan jam 07 kembali jadi 08.
 | 
8
 | reset
 | Alat keempat adalah git reset. Perintah ini memindahkan penunjuk branch mundur, seolah-olah commit sesudahnya tidak pernah ada. Pilihan soft tetap menyimpan perubahannya di staging. Pilihan hard membuang semuanya, termasuk isi folder kerja.
 | Diagram: label main bergeser mundur; dua jalur warna untuk --soft dan --hard (label merah).
 | 
9
 | Kesalahan
 | Sekarang kita buat kesalahan yang sering terjadi. Raka ingin membatalkan satu commit, tetapi salah mengetik angka dan menjalankan git reset dash dash hard HEAD tilde tiga. Tiga commit langsung hilang dari git log, termasuk fitur panggil nomor yang dikerjakan seharian.
 | git reset --hard HEAD~3 (label merah), git log --oneline tinggal 2 commit. Diagram: 3 titik memudar.
 | 
10
 | reflog
 | Jangan panik dulu. Git diam-diam mencatat setiap perpindahan HEAD di buku harian yang disebut reflog. Di sana kita masih bisa melihat hash commit sebelum reset. Dengan reset ke hash itu, ketiga commit kembali utuh.
 | git reflog, sorot baris sebelum "reset: moving to HEAD~3"; git reset --hard <hash>; diagram: 3 titik muncul lagi.
 | 
11
 | Batasnya
 | Ingat, reflog hanya menyelamatkan yang pernah di-commit. Perubahan yang belum pernah di-commit lalu dibuang dengan reset hard benar-benar hilang. Karena itu, sering-seringlah commit.
 | Kartu peringatan.
 | 
12
 | Rangkuman
 | Mari kita rangkum. Restore untuk perubahan yang belum di-commit. Amend untuk memperbaiki commit terakhir. Revert untuk membatalkan commit yang sudah dibagikan. Reset untuk merapikan commit lokal, dan reflog untuk menyelamatkan diri setelah salah reset.
 | Tabel ringkas: keadaan dan alatnya.
 | 
13
 | Tantangan
 | Tantangan untukmu: buat tiga commit, jalankan reset hard ke commit pertama, lalu kembalikan semuanya dengan reflog. Di episode berikutnya, kita belajar branch, supaya kamu bisa mencoba ide baru tanpa merusak kode yang sudah jalan.
 | Kartu tantangan + judul G03.

G03 Branch: Kerja Paralel tanpa Saling Ganggu
Kait: "Setelah menonton, kamu bisa mencoba fitur baru di branch sendiri tanpa merusak kode yang sudah jalan."
No
 | Bagian
 | Narasi (Cahaya)
 | Visual
 | 
1
 | Kait
 | Pak Rahmat minta fitur baru: layar TV harus membacakan nomor antrean. Di saat yang sama, ada bug kecil yang harus segera diperbaiki. Setelah menonton video ini, kamu bisa mengerjakan fitur baru di branch sendiri, tanpa merusak kode yang sudah jalan.
 | Diagram: satu garis commit bercabang dua, label "fitur suara" dan "perbaikan bug". Kartu judul.
 | 
2
 | Prasyarat
 | Video ini melanjutkan episode commit dan episode mundur ke masa lalu. Kalau kamu belum paham apa itu commit dan HEAD, tonton dulu kedua episode itu.
 | Thumbnail kecil G01 dan G02.
 | 
3
 | Salah paham
 | Banyak orang mengira branch adalah salinan folder. Padahal, branch hanyalah label kecil yang menempel di satu commit. Membuat branch baru tidak menyalin satu berkas pun, sehingga prosesnya sangat cepat.
 | Diagram: folder disalin dicoret; diganti label main yang menempel di titik commit.
 | 
4
 | HEAD
 | Lalu, apa itu HEAD? HEAD adalah penanda "kamu di sini". HEAD menunjuk ke branch yang sedang kamu pakai. Setiap kali kamu commit, label branch itu maju ke commit yang baru, dan HEAD ikut bersamanya.
 | Diagram: label hitam HEAD di atas main; commit baru, keduanya bergeser maju.
 | 
5
 | Membuat branch
 | Kita buat branch untuk fitur suara dengan git switch dash c, lalu nama branch-nya. Nama branch sebaiknya pendek dan menjelaskan isinya, misalnya fitur slash suara-panggilan.
 | git switch -c fitur/suara-panggilan; diagram: label kedua muncul di titik yang sama, HEAD pindah ke label itu.
 | 
6
 | Commit di branch
 | Sekarang kita tulis kode pemanggil suara, lalu commit dua kali. Perhatikan diagramnya. Label fitur maju, sedangkan label main tetap diam di tempatnya.
 | Ketik fungsi bacakanNomor di public/tv.js, dua commit; diagram: label fitur maju 2 titik.
 | 
7
 | Pindah branch
 | Tebak dulu: kalau kita pindah kembali ke main, apa yang terjadi pada berkas tv titik js di editor?
 | git switch main belum dijalankan; "Tebak dulu" + hitung mundur.
 | 
8
 | Jawaban
 | Kode pemanggil suara menghilang dari editor. Kodenya tidak terhapus. Git hanya menampilkan isi proyek sesuai commit tempat main berada. Kalau kita pindah lagi ke branch fitur, kodenya muncul kembali.
 | git switch main: isi tv.js berubah di editor; git switch fitur/suara-panggilan: muncul lagi.
 | 
9
 | Kesalahan
 | Sekarang kita buat kesalahan yang sering terjadi. Raka memperbaiki bug nomor ganda, lalu langsung commit, tanpa sadar ia masih berada di branch fitur. Perbaikan bug itu sekarang tercampur dengan fitur yang belum selesai.
 | Status bar VS Code menunjukkan nama branch fitur; commit "Perbaiki nomor ganda" masuk ke branch fitur. Label merah "Salah branch".
 | 
10
 | Perbaikan
 | Kita pindahkan commit itu ke tempat yang benar. Kita kembali ke main, lalu ambil commit itu dengan git cherry-pick dan hash-nya. Setelah itu, commit tersebut kita buang dari branch fitur dengan git revert.
 | git switch main, git cherry-pick <hash>; diagram: salinan titik muncul di main. Di branch fitur: git revert <hash>.
 | 
11
 | Kebiasaan
 | Supaya tidak terulang, biasakan melihat nama branch sebelum commit. VS Code menampilkannya di pojok kiri bawah, dan git status menyebutkannya di baris pertama.
 | Zoom ke status bar dan baris "On branch ...".
 | 
12
 | Merge fast-forward
 | Fitur suara sudah selesai, jadi kita gabungkan ke main dengan git merge. Karena main belum bergerak sejak branch dibuat, Git cukup menggeser label main maju. Penggabungan ini disebut fast-forward.
 | Contoh dengan branch kecil lain: git merge, keluaran "Fast-forward"; diagram: label main meluncur maju.
 | 
13
 | Merge commit
 | Kalau main sudah punya commit baru, Git membuat commit gabungan yang punya dua induk. Hasilnya terlihat jelas di git log dash dash graph. Setelah itu, branch fitur boleh dihapus, karena isinya sudah ada di main.
 | git merge fitur/suara-panggilan, git log --oneline --graph, git branch -d; diagram: titik dengan dua panah masuk.
 | 
14
 | Rangkuman
 | Mari kita rangkum. Branch adalah label yang menunjuk ke commit, dan HEAD menandai posisimu. Switch dash c membuat branch baru, merge menggabungkannya, dan sebelum commit, selalu periksa dulu nama branch-mu.
 | Kartu rangkuman.
 | 
15
 | Tantangan
 | Tantangan untukmu: buat dua branch dari commit yang sama, buat satu commit di masing-masing branch, lalu gabungkan keduanya ke main. Di episode berikutnya, kita lihat apa yang terjadi kalau dua branch mengubah baris yang sama.
 | Kartu tantangan + judul G04.

G04 Merge Conflict: Membaca dan Membereskannya
Kait: "Setelah menonton, kamu bisa membaca tanda merge conflict dan membereskannya tanpa kehilangan kode siapa pun."
No
 | Bagian
 | Narasi (Cahaya)
 | Visual
 | 
1
 | Kait
 | Kamu menjalankan git merge, lalu muncul tulisan CONFLICT, dan kodemu tiba-tiba penuh tanda panah aneh. Setelah menonton video ini, kamu bisa membaca tanda merge conflict dan membereskannya, tanpa kehilangan kode siapa pun.
 | Terminal: CONFLICT (content): Merge conflict in antrean.js; editor dengan <<<<<<<. Kartu judul.
 | 
2
 | Prasyarat
 | Video ini melanjutkan episode branch. Kamu perlu tahu cara membuat branch dan menggabungkannya dengan git merge.
 | Thumbnail G03.
 | 
3
 | Bukan error
 | Pertama, tenang dulu. Konflik bukan error, dan tidak ada yang rusak. Konflik adalah cara Git bertanya kepadamu, karena ada dua perubahan pada baris yang sama, dan Git tidak mau menebak mana yang benar.
 | Diagram: dua panah dari dua branch menuju satu baris, di tengahnya tanda tanya.
 | 
4
 | Kapan terjadi
 | Kalau dua orang mengubah bagian berkas yang berbeda, Git menggabungkannya sendiri. Konflik hanya muncul kalau keduanya mengubah baris yang sama, atau kalau satu orang menghapus berkas yang sedang diubah orang lain.
 | Diagram berkas: perubahan di baris 3 dan baris 20 bergabung mulus; perubahan dua-duanya di baris 12 berwarna merah.
 | 
5
 | Skenario
 | Raka dan Nadia sama-sama mengubah fungsi formatNomor. Raka menambahkan kode layanan, sehingga nomornya menjadi S001 untuk servis. Nadia menambahkan tanda strip supaya lebih mudah dibaca di TV, sehingga nomornya menjadi A-001.
 | Dua branch: raka/kode-layanan dan nadia/strip-nomor, masing-masing dengan git diff pada baris yang sama.
 | 
6
 | Tebak dulu
 | Branch Nadia sudah digabung ke main. Sekarang kita gabungkan branch Raka. Tebak dulu: apakah Git bisa menggabungkannya sendiri?
 | git merge raka/kode-layanan belum dijalankan; "Tebak dulu" + hitung mundur.
 | 
7
 | Konflik muncul
 | Tidak bisa. Git melaporkan konflik di antrean titik js. Git status juga menyebutkan berkas itu sebagai both modified, artinya diubah oleh kedua pihak.
 | Keluaran CONFLICT, git status dengan both modified. Diagram: merge berhenti di tengah.
 | 
8
 | Membaca tanda
 | Mari kita baca tandanya. Di antara tanda kurang dari tujuh kali dan tanda sama dengan, ada versi milik kita, yaitu main, yang berisi perubahan Nadia. Di antara tanda sama dengan dan tanda lebih dari, ada versi yang datang dari branch Raka. Tugas kita adalah memilih, atau menggabungkan keduanya.
 | Zoom ke blok konflik; tiga penanda diberi label: "versi main (Nadia)", "pemisah", "versi Raka". Seluruh blok terlihat, tidak terpotong.
 | 
9
 | Membereskan
 | Di sini, kedua perubahan sama-sama dibutuhkan. Jadi kita gabungkan menjadi S-001: kode layanan dari Raka, dan tanda strip dari Nadia. Lalu kita hapus ketiga penanda konflik. VS Code juga menyediakan tombol Accept Current, Accept Incoming, dan Accept Both, tetapi hasilnya tetap harus kamu periksa.
 | Sorot tombol Accept di atas blok; tulis versi gabungan secara manual; penanda dihapus.
 | 
10
 | Selesaikan merge
 | Setelah berkasnya beres, kita uji dulu aplikasinya. Nomornya tampil sebagai S-001, sesuai harapan. Lalu kita jalankan git add dan git commit untuk menyelesaikan merge.
 | node server.js, buka halaman, nomor S-001 tampil. git add antrean.js, git commit. Diagram: merge commit terbentuk.
 | 
11
 | Kesalahan
 | Sekarang kita lihat kesalahan yang sering terjadi. Di merge berikutnya, ada dua blok konflik. Raka hanya membereskan yang pertama, lalu langsung commit. Git tidak melarangnya. Saat server dijalankan, muncul SyntaxError, karena penanda konflik ikut tersimpan di kode.
 | Commit dengan sisa <<<<<<<; node server.js → SyntaxError: Unexpected token '<<'. Label merah.
 | 
12
 | Perbaikan
 | Untuk menemukan sisa penanda, jalankan git grep dengan tanda kurang dari tujuh kali. Kita bereskan blok kedua, uji lagi, lalu commit perbaikannya. Biasakan menjalankan tes atau aplikasimu setelah setiap merge.
 | git grep -n "<<<<<<<" menunjukkan baris; perbaiki, server jalan, commit.
 | 
13
 | Jalan keluar
 | Kalau di tengah merge kamu merasa bingung, kamu boleh membatalkannya dengan git merge dash dash abort. Proyek kembali seperti sebelum merge, dan kamu bisa bertanya dulu kepada temanmu.
 | git merge --abort, git status bersih.
 | 
14
 | Rangkuman
 | Mari kita rangkum. Konflik muncul kalau dua perubahan menyentuh baris yang sama. Baca kedua versinya, pilih atau gabungkan, hapus semua penanda, uji aplikasinya, lalu add dan commit. Kalau bingung, merge abort.
 | Kartu rangkuman 5 langkah.
 | 
15
 | Tantangan
 | Tantangan untukmu: buat dua branch yang mengubah baris yang sama, gabungkan keduanya, lalu bereskan konfliknya. Di episode berikutnya, kita kirim kode ke server dan belajar pull request.
 | Kartu tantangan + judul G05.

G05 Remote dan Pull Request
Kait: "Setelah menonton, kamu bisa mengirim kode ke server Git dan mengajukan pull request supaya kodemu diperiksa teman sebelum digabung."
No
 | Bagian
 | Narasi (Cahaya)
 | Visual
 |

3
 | Konsep remote
 | Repository di server disebut remote, dan biasanya diberi nama origin. Push mengirim commit dari laptop ke remote. Fetch mengambil commit baru dari remote tanpa mengubah kodemu. Pull adalah fetch yang langsung diikuti merge.
 | Diagram: kotak Laptop dan kotak Remote; panah push ke atas, fetch ke bawah, pull = fetch + merge.

 | Jangan force
 | Di internet, banyak saran untuk memakai git push dash dash force. Jangan lakukan itu di branch bersama, karena commit Nadia di server akan terhapus. Cara yang benar adalah git pull, periksa hasil gabungannya, lalu push lagi. Kalau Git bertanya cara menggabungkan, untuk sekarang pilih merge dengan git config pull titik rebase false. Pilihan rebase kita bahas di episode terakhir.

 | Alur besar
 | Inilah alur yang dipakai banyak tim. Tugas ditulis sebagai issue. Untuk setiap issue, buat branch dari main yang terbaru. Kerjakan dengan commit-commit kecil, push, lalu buka pull request. Setelah di-review dan lolos tes, gabungkan ke main. Saat siap dirilis, beri tag versi.

4
 | Pesan commit
 | Pesan commit yang baik menjawab pertanyaan: apa yang berubah? Banyak tim memakai awalan seperti feat untuk fitur baru, fix untuk perbaikan bug, dan docs untuk dokumentasi. Contohnya, fix: nomor antrean kembali ke satu setiap hari.

5
 | Kesalahan: commit raksasa
 | Sekarang kita lihat kesalahan yang sering terjadi. Raka mengubah tiga hal sekaligus, yaitu perbaikan bug, tampilan tombol, dan teks bantuan, lalu menyimpannya dalam satu commit berpesan update. Kalau satu bagian bermasalah, ketiganya ikut terseret.
 | git diff --stat menunjukkan 3 berkas, 1 pesan "update". Label merah.

6
 | Perbaikan: add -p
 | Kita batalkan commit itu dengan reset soft, sehingga perubahannya kembali ke staging. Lalu, dengan git add dash p, Git menanyakan setiap potongan perubahan satu per satu. Kita jawab y untuk yang mau dimasukkan, dan n untuk yang tidak. Hasilnya tiga commit kecil dengan pesan yang jelas.
 | git reset --soft HEAD~1, git restore --staged ., git add -p dengan jawaban y/n terlihat; tiga commit; git log --oneline.
 |

 | Stash
 | Di tengah pekerjaan, Nadia diminta memperbaiki bug mendesak di main, padahal kodenya belum siap di-commit. Ia menyimpannya sementara dengan git stash. Setelah bug selesai, git stash pop mengembalikan pekerjaannya.
 | Kanan: git stash, git switch main, perbaiki, commit, kembali, git stash pop; diagram: laci tempat menyimpan.

8
 | Tebak dulu
 | Sebelum membuka pull request, branch Raka tertinggal dari main. Ia bisa menggabungkan main dengan merge, atau memakai pull dash dash rebase. Tebak dulu: apa bedanya bagi sejarah proyek?
 | Diagram dua kemungkinan, ditutup tulisan "Tebak dulu".

9
 | Merge vs rebase
 | Merge menambah satu commit gabungan, sehingga sejarahnya bercabang. Rebase memindahkan commit Raka ke ujung main yang terbaru, sehingga sejarahnya lurus dan mudah dibaca. Aturannya, rebase hanya untuk commit milikmu yang belum dipakai orang lain, karena rebase mengganti hash commit.
 | Animasi: (a) merge commit dengan dua induk; (b) titik-titik Raka terangkat lalu ditempel di ujung main dengan hash baru. Lalu git pull --rebase origin main di terminal.
 |

 | Cek kerjaan AI
 | Banyak editor sekarang bisa membuatkan pesan commit dengan AI. Itu membantu, tetapi selalu bandingkan pesannya dengan git diff. Di contoh ini, AI menulis bahwa commit menambah validasi, padahal diff juga menghapus satu pengecekan. Pesan yang salah sama berbahayanya dengan tidak ada pesan.
 | Label jujur "contoh pesan bergaya hasil AI". Pesan saran vs git diff dengan baris merah yang dihapus disorot.

11
 | Tag dan rilis
 | Setelah semua fitur versi pertama digabung, kita beri tanda dengan git tag v1 titik 0 titik 0, lalu kita kirim tag itu ke server. Kalau versi berikutnya bermasalah, tim selalu tahu titik mana yang terakhir stabil.
 | git tag -a v1.0.0 -m "Rilis pertama SiAntre", git push origin v1.0.0; halaman Releases/Tags di Gitea; diagram: bendera pada titik.
 | 
12
 | Rangkuman seri
 | Mari kita rangkum seluruh seri. Commit kecil dengan pesan jelas. Satu branch untuk satu tugas. Bereskan konflik dengan tenang, lalu uji. Push lewat pull request dan saling review. Rebase hanya untuk commit milikmu sendiri, dan beri tag setiap rilis.
 | Kartu rangkuman 6 kebiasaan.

G01
 | Password-mu ikut ter-commit?
 | Kamu mengetik git add titik, lalu commit. Rasanya aman, padahal berkas titik env yang berisi password database ikut tersimpan. Kalau proyek itu diunggah, password-mu bisa dibaca siapa saja. Sebelum commit pertama, keluarkan dulu berkas itu dengan git rm dash dash cached, lalu tulis titik env di berkas titik gitignore. Sejak saat itu, Git tidak akan menyimpannya lagi. Cara lengkapnya ada di episode Git dari Nol.
 | git add ., git status dengan .env hijau, isi .env disorot, git rm --cached .env, .gitignore.
 | 
G02
 | Kerjaan hilang setelah reset? Belum tentu.
 | Kamu salah mengetik, lalu menjalankan git reset dash dash hard HEAD tilde tiga. Tiga commit hilang dari git log, termasuk kerjaan seharian. Tenang dulu. Git punya buku harian bernama reflog yang mencatat setiap posisi HEAD. Cari hash sebelum reset, lalu reset ke hash itu, dan semua commit kembali. Ingat, cara ini hanya berhasil untuk yang sudah pernah di-commit. Tonton episode lengkapnya untuk empat cara mundur yang aman.
 | reset --hard HEAD~3 (label merah), git log pendek, git reflog, reset ke hash, commit kembali.
 | 
G03
 | Branch itu bukan salinan folder.
 | Banyak orang mengira branch adalah salinan folder proyek. Padahal, branch hanyalah label kecil yang menempel di satu commit. Saat kamu commit, label itu maju. Saat kamu pindah branch, Git menampilkan isi proyek sesuai commit tempat label itu berada. Karena itu, membuat branch sangat cepat, dan kamu bebas mencoba ide baru tanpa merusak main. Lihat cara kerjanya di episode branch.
 | Diagram label bergerak + git switch yang mengubah isi editor.
 | 
G04
 | Konflik itu bukan error.
 | Muncul tulisan CONFLICT setelah git merge? Itu bukan error. Git sedang bertanya, karena ada dua perubahan pada baris yang sama. Bagian atas adalah versimu, dan bagian bawah adalah versi yang datang. Pilih atau gabungkan keduanya, hapus semua penanda, lalu uji aplikasinya. Kalau penandanya tertinggal, aplikasimu bisa langsung error. Cara lengkapnya ada di episode merge conflict.
 | Blok konflik dengan label, versi gabungan, lalu SyntaxError dari sisa penanda.
 | 
G05
 | Push ditolak? Jangan force dulu.
 | Push-mu ditolak dengan tulisan rejected? Artinya, temanmu sudah mengirim commit yang belum ada di laptopmu. Kalau kamu memakai push dash dash force, commit temanmu di server bisa terhapus. Cara yang benar adalah git pull dulu, periksa hasil gabungannya, lalu push lagi. Pelajari juga cara kerja pull request di episode lengkapnya.
 | Layar dibagi dua, pesan rejected, label merah --force, git pull, push berhasil.
 | 
G06
 | Pesan commit "fix" itu utang.
 | Tiga bulan lagi, kamu membuka sejarah proyek dan hanya menemukan pesan fix, update, dan coba lagi. Tidak ada yang tahu kapan bug itu masuk. Mulai sekarang, buat commit kecil, dan tulis apa yang berubah, misalnya fix: nomor antrean kembali ke satu setiap hari. Kalau terlanjur membuat commit besar, pecah dengan git add dash p. Alur lengkapnya ada di episode kerja tim sehari-hari.
 | Log penuh "fix", lalu git add -p, log rapi.
